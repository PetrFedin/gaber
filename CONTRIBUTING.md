# GABER — правила разработки и интеграции

Рабочий источник: [PR #2](https://github.com/PetrFedin/gaber/pull/2), ветка feat/production-engineering-v04. Не менять main напрямую и не создавать вторую конкурирующую интеграционную версию. До прохождения release gates проект остаётся PRODUCTION HOLD.

## Перед изменением

1. Прочитать [текущий статус](docs/STATUS.md), [три роли](docs/THREE-ROLE-PLATFORM-CONTRACT.md) и [карту исходников](docs/PROJECT-STRUCTURE.md).
2. Проверить, не существует ли реализация в соседнем модуле. Изменения трассируются по UI, домену, server admission/DTO, данным и тестам.
3. Не превращать историю проверки в требования: старые шесть ролей отменены.
4. Не коммитить .env, токены, платёжные реквизиты, персональные данные, node_modules, dist, тестовые дампы БД.

## Минимальный локальный контроль

Нужны Git и Node.js версии из .nvmrc:

~~~sh
npm ci
npm run verify:repository
npm test
npm run build
~~~

Команда verify:repository проверяет Git blob-инвентаризацию и правила структуры. Для намеренно изменённых отслеживаемых файлов перед коммитом выполнить npm run snapshot:source, затем повторить verify:repository. Нельзя обновлять manifest ради сокрытия непонятного изменения: сначала выяснить источник diff.

Исполняемые PostgreSQL и Chromium проверки дополняют этот набор согласно [воротам ревью](docs/RELEASE-REVIEW-GATES.md). Локальный PASS не подменяет Actions на точном SHA.

## Изменения модулей и контрактов

- Именовать компоненты React в PascalCase, доменную логику в описательных JS-модулях, тесты с соответствующим предметным именем.
- Не переносить пачками исходники и не ломать публичные импорты ради «красивой» дерева; отдельный перенос сопровождается регрессией.
- Фиксировать точные копейки, ревизии заказа, субъект и tenant. Проверять отрицательные сценарии доступа и конкурентные операции.
- Новый SQL — миграция с очередным номером, тестом на чистой PostgreSQL и ясной rollback/compatibility стратегией.
- Обновлять [README](README.md), [карту кода](docs/PROJECT-STRUCTURE.md) при изменении архитектуры и [status](docs/STATUS.md) при новой проверке. Новые тестовые результаты не приписывать прошлому SHA.

## PR и выпуск

В PR указывать цель, роли, изменённые контракты, файлы/миграции, риск, rollback, команды и ссылки на доказательства. Использовать [шаблон проверки](.github/pull_request_template.md). Отдельный reviewer не должен быть автором изменений. Только проверенный GREEN на одном SHA плюс независимый review открывают вопрос о merge; реальные деньги и фабричное производство требуют отдельной сертификации.
