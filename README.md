# GABER — цифровое мебельное ателье

Параметрический конструктор мягкой мебели и инженерный прототип связанного заказа: конфигурация → BOM → предварительная стоимость → предложение → согласование → исполнение → приёмка.

**Инженерная версия v0.4.19 · Draft PR #2 · PRODUCTION HOLD.**

**Визуальный конструктор:** исправляются высота и глубина сиденья, наклон спинки, физический масштаб процедурной фактуры, объёмные швы и цилиндрическая подушка-валик. В Studio добавлены режимы детализации и экспорт визуального 3D-эскиза GLB; это **не** утверждённая CAD/КД. Статус проверки и дальнейшая программа: [качество конструктора](docs/CONSTRUCTOR-QUALITY.md). Данные не в production.

**Только три роли: клиент · фабрика · партнёр GABER (оператор платформы).** Партнёр рассчитывает себестоимость, ТЗ, клиентскую цену и свою комиссию; фабрика получает проектное ТЗ и подтверждает либо возвращает его; лишь затем клиенту доступно предложение. [Единый бизнес-контракт и права](docs/THREE-ROLE-PLATFORM-CONTRACT.md). Проектная цена и расчёт не являются проверенными платежами или производственным допуском.

**Единый интеграционный источник:** [PR #2](https://github.com/PetrFedin/gaber/pull/2) (`feat/production-engineering-v04`); `main` пока остаётся v0.2. Все исходники, порядок проверки и правила интеграции: [воспроизводимость и сводный статус](docs/REPRODUCIBILITY.md). Для контроля состава файлов используйте `npm run verify:source`; его результат не заменяет тесты, браузер, PostgreSQL и серверную авторизацию. Эта инструкция относится к ветке `feat/production-engineering-v04`. Содержимое `main` и опубликованного сайта может отличаться.

## Канонические роли и кабинеты

**Клиент:** `#projects` — 3D-конструктор, запросы и оплаты. **Фабрика:** `#factory` — подтверждение ТЗ и исполнение. **Партнёр GABER (мы):** `#partner` — все сделки, расчёты, BOM/ТЗ, клиентские предложения, наша комиссия и контроль. Переписка заказов разделена на `client_partner`, `factory_partner` и общий `shared`; партнёр видит оба двусторонних диалога, клиент и фабрика — только свой и общий. В PostgreSQL это пока staging-контракт 005, не проверенное production. Старый шестиролевой проектный контракт и приватные треды внешних партнёров отменены; исторические документы остаются для аудита, не как действующие правила. Демо-переключение вкладок **не** равно авторизации. Реальные данные пока не использовать.

## Что реализовано

- Пять мебельных категорий, параметры, материалы, размеры, детали и механизмы; Three.js и SVG fallback, инспекционная сборка.
- Связанные идентификаторы геометрии, деталей, мягких слоёв, подвески, узлов и технологических маршрутов; проверка комплектности цифрового пакета.
- Демонстрационная калькуляция; источники заводских вводов, черновики/ревизии, анализ покрытия и отклонений.
- Локальные проекты, резервные экспорты и восстановление с отказом от повреждённых/устаревших записей.
- Локальный заказ: ревизии КП, согласование, заявленные/учтённые платежи, перенос аванса, сценарий QC/отгрузки/доставки, претензия и принятие решения.
- Локальный операционный обзор и очередь действий.
- Серверные библиотеки: права шести ролей, admission команд, журнал с хеш-цепочкой, версиями и идемпотентностью, PostgreSQL-адаптеры и две SQL-миграции.
- Новое в v0.4.19: `service.read({principal,request:{orderId}})` с проверкой доступа до чтения журнала и отдельными DTO; точные копейки во всех суммах заказа; единая местная дата аналитики при обновлении.

## Что ещё не подключено

UI использует **localStorage**, не серверный журнал. Нет работающего входа, session verifier, HTTP API, подключённой PostgreSQL и синхронизации устройств. Серверный `principal` должен создаваться проверенным middleware; строковое поле `identitySource` само по себе не аутентификация. Ролевые DTO не заменяют проверку подписи/отзыва сессии.

Денежные записи не подтверждены банком. Производственные события и документы не подтверждены фабрикой/перевозчиком. CAD, лекала, нормы времени, материалы, испытания и полная конечная цена не приняты. Производственный допуск остаётся закрыт. Не вводите реальные конфиденциальные данные в локальный прототип.

## Запуск и проверка

Node.js 24 используется в CI.

```sh
npm ci
npm test
npm run build
npm run dev
```

`npm test` запускает Node, SSR и DOM-проверки, включая деньги и смену календарной даты. Это не Chromium, WebGL или PostgreSQL integration test. Успешный локальный прогон не означает GREEN GitHub Actions; точные результаты записаны в документе проверки.

Статическая сборка — `dist/`, маршруты через hash. Серверные модули не импортируются клиентским Vite entry и требуют отдельного будущего bootstrap.

## Правила развития

Каждая функция проходит цепочку UI → домен → данные → права → проверка → документация. Платежи — в целых копейках; неподтверждённые факты не становятся выручкой или допуском. Выпуск требует одного проверенного SHA, БД/RLS, независимых аккаунтов, браузерных сценариев и отдельной заводской приёмки.

Сторонние зависимости сохраняют собственные лицензии; публичная лицензия на код проекта не объявлена. Собственные цифровые формы не выдаются за модели сторонних мебельных брендов.
