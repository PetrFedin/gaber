# GABER — матрица сквозной приёмки ролей

**Статус 30.10.2026: инженерная интеграция в [PR #2](https://github.com/PetrFedin/gaber/pull/2).** Все исходники работают в одном рабочем дереве. **PRODUCTION HOLD**.

## Обнаруженные и исправленные разрывы

1. **Параллельные пути чтения API.** Старый HTTP GET использовал отдельные `readOrder` и `authorize` с минимальной сводкой, а сервис журнала имел собственные ACL, проверку SHA-цепочки и шесть DTO. Новый `GET /api/v1/orders/:id` вызывает только `journal.read({principal,request:{orderId}})`; чтение разрешается до доступа к событиям и возвращает проекцию разрешённой роли.
2. **Партнёр без переписки.** Политика разрешала `orders.message` партнёру, а admission требовал только роли `client/factory`. Теперь авторская роль выводится из проверенного server principal. Партнёр может писать только в собственный `partnerId`-тред, который привязан к `resource.partnerIds`. Второй партнёр не видит первый тред.
3. **Скрытое сообщение бренда.** Бренд может отправлять только общие сообщения; ему запрещено записывать сообщение в партнёрский тред, которого он сам не видит.
4. **Разрозненные роли технолога.** Старые `technologist/factory-admin` в Factory Review не совпадали с `factory-technologist/owner` в шести-ролях сервера. Проверка фабричной документации использует только общие серверные роли, обязательные tenantId/factoryId, MFA и связанный с сессией factory-scoped repository.
5. **Схема БД не знала роли переписки.** Добавлена **неприменённая** миграция `server/migrations/003_scoped_order_messages_hold.sql`: новая проверка роли и partner thread, обязательные JSON-ключи, корректный expectedVersion, отсутствие SQL CHECK NULL loopholes. Нужна реальная PostgreSQL 17-аттестация и ревью DBA.

## Матрица прав для одного заказа

| Роль | Чтение | Переписка | Предложение | Согласование / деньги | Производство |
|---|---|---|---|---|---|
| Клиент | Конфигурация, условия, локальные платежи | Общая и назначенный партнёр | Нет | Согласие/корректировка/заявление об оплате | Не имеет права выпускать |
| Бренд | Конфигурация и предложенные условия | Только общая | Да, с MFA | Не получает банковские поля | Не выпускает |
| Партнёр | Этап, ревизия и **свой** тред | Только тред своего partnerId | Нет | Нет | Нет |
| Оператор фабрики | Заказ, технический состав, локальные записи | Общая и назначенный партнёр | Да, с MFA | Только запись **неподтверждённого** платежа | Реальная команда запуска запрещена |
| Технолог фабрики | Конфигурация, ревизия, технические сведения | Нет | Нет | Нет | Техническая **проверка документации** с MFA, не выпуск |
| Владелец | Данные назначенного tenant | Общая и назначенный партнёр | Да, с MFA | Локальные данные; не банковский факт | Не выпускает без внешнего полномочия |

## Исполняемые сценарии

`tests/role-interactions-e2e.test.js` — реальные Node HTTP-запросы по loopback к `createOrderHttpServer`, настоящий `orderJournalService`/admission/reducer/read DTO, **семь независимых тестовых токенов** для шести ролей (два партнёра), и транзакционный in-memory repository с сериализацией конкурентных действий. Это **не** настоящий PostgreSQL, не реальный провайдер аутентификации и не Playwright/Chromium.

- Независимые токены читают один и тот же номер версии и только разрешённые поля; партнёры P1/P2 не видят чужие сообщения.
- Клиент создаёт заказ → бренд предлагает цену → клиент принимает → два партнёра общаются отдельно → фабрика вносит неподтверждённый платёж → все роли читают свою проекцию.
- Фальсификация роли/актора, чужая организация и неприкреплённый участник, отсутствие MFA, отзыв и истечение токена отклоняются.
- Новая ревизия сбрасывает согласие и требует повторного принятия клиентом. Старый revisionId не принимается.
- Параллельные POST с одинаковой версией: один коммит, второй получает конфликт. Повтор с идентичным ключом идемпотентен, подмена тела с тем же ключом запрещена.
- Ни локальная запись денег, ни техническая проверка не разрешают реальные `start`, `ship` или `productionRelease`.

## Команды чистой приёмки на одном SHA

```bash
git fetch origin
git switch --detach <PR_2_HEAD_SHA>
nvm install
nvm use
npm ci
npm run verify:source
node --test tests/role-interactions-e2e.test.js tests/order-http-api-v0419.test.js \
  tests/order-read-v0419.test.js tests/order-command-admission-v0417.test.js \
  tests/factory-review-policy.test.js tests/factory-review-service.test.js
npm test
npm run build
```

Если какая-либо из проверок выдаёт FAIL — исправить код, обновить inventory, повторить весь цикл на **новом** SHA. Не объявлять готовность только по отдельным тестам. CI GREEN не заменяет PostgreSQL и браузерную приёмку.

### Незавершённые требования

1. Развернуть настоящие независимые app/backend/database окружения для двух организаций, два tenant и реальные проверяемые/отзываемые сессии.
2. Проверить миграции 001–003 непривилегированным DB-пользователем: `INSERT` с null/отсутствующими ключами, PK/FK/RLS, конкурентность, COMMIT failure, backup/restore и назначение partner_ids.
3. Проверить клиент/бренд/партнёр/оператор/технолог/владелец в отдельных браузерных контекстах при разрешениях и при отзывах доступа, на 375/768/1440.
4. Внедрить действительную общую серверную историю для `OrderWorkspace`: сейчас UI по-прежнему хранит демонстрационные события в localStorage. HTTP тест без подключения UI **не** является сквозным продуктовым E2E.
5. Реальные квитанции PSP, изменения ревизий, полная цена, утверждённая CAD/BOM, выпуск в производство, QC, отгрузка, доставка и возвраты должны подтверждаться внешними сервисами.
6. Нужен независимый security/code review, фактический запуск Actions и визуальная приёмка без демо-ИИ.
