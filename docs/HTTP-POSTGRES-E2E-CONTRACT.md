# GABER: HTTP → Postgres 17 → 3 роли (staging-only)

**Новый интеграционный контракт.** Код теста добавлен в единый Draft PR #2.
До получения фактических логов не заявлять его PASS.

## Как устроена проверка

В `postgres-staging` на GitHub-hosted runner в одноразовом PostgreSQL 17
сначала применяются миграции `001–007`, затем выполняется существующий
SQL/RLS contract. После этого создаются фиктивные `TENANT-API-A/B`,
подтверждённые исключительно **для теста** фабрики и отдельная LOGIN DB-роль
`gaber_http_ci`. Она не является superuser, `BYPASSRLS` выключен и
права наследуются только от ограниченного `gaber_runtime_contract`.

Node.js запускает **настоящий HTTP-сервер** `createOrderHttpServer`, сервис
`wirePostgresOrderJournal`, `pg.Pool` и настоящие SQL-запросы. Разрешённые
сессии выдаёт **локальный тестовый резолвер** с независимыми случайными
Bearer-токенами, отдельными actor/tenant/client/factory scope.
Токены здесь — фикстуры; это **не** реализация IdP или реальной MFA.

Тест подтверждает:
- Запрос клиента без заранее созданного `order_resources`, атомарность
  `resource + head + event`, повторную идемпотентность.
- Права клиента, оператора и фабрики; фабрика не получает клиентскую цену
  и комиссию, клиент не получает производственную себестоимость.
- Незарегистрированная фабрика, фабрика другого tenant, приостановленная
  фабрика и второе назначение не получают доступ или назначение.
- ТЗ → ответ фабрики → предложение → согласование → два типа
  **неподтверждённых** платёжных записей; выпуск производства запрещён.
- Приватность `client_partner` и `factory_partner`; отзыв фабричного
  допуска во время цикла блокирует её чтение и запись.
- Запрос на изменение R1, новый S2 и R2, запрет согласовать старую ревизию.
- Конкурентные SQL-транзакции с одним успешным событием и stale-конфликтом.
- Один `orderId` у двух tenant не приводит к утечке; отдельное прямое
  SQL-чтение с tenant-scoped runtime user отсекает чужие записи.
- Тестовый отзыв серверного токена сразу закрывает доступ HTTP.

Все фикстуры изолированы в disposable базе; команда никогда не подключается
к production DB или внешнему PSP. После шага печатается
`GABER_POSTGRES_HTTP_E2E_GREEN` **только при успехе всех проверок**.

## Что остаётся открытым

Нужны реальные авторизованные сеансы и отзыв через IdP/MFA, привязка
существующего фронтенда к HTTP API и persistent PostgreSQL staging,
межустройственный сценарий, долговременный backup/restore,
реальный PSP sandbox и верифицированный заводской производственный пакет.
Проверка трех локально выданных тестовых токенов не заменяет данные
настоящих пользователей и юридическую верификацию фабрики.
