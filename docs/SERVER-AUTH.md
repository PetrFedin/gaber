# GABER — серверный вход и сессии (код-часть issue #5)

Ветка `gaber-v04-auth` добавляет к серверным библиотекам v0.4 то, чего им не хватало: настоящие учётные записи, пароли, сессии и точку запуска сервера. **PRODUCTION HOLD сохраняется.** Это не MFA, не проверка личности организаций, не онбординг фабрик и не готовность к реальным заказам.

## Что добавлено

| Часть | Файлы | Суть |
| --- | --- | --- |
| Схема | server/migrations/008_auth_sessions_hold.sql | `gaber_auth.users` и `sessions`; роль БД `gaber_auth_runtime` отдельно от роли заказов |
| Пароли | server/auth/passwords.js | argon2id, выравнивание времени для неизвестной почты |
| Сессии | server/auth/authStore.js | токен 32 байта, в базе только SHA-256; срок, отзыв, блокировка пользователя |
| Principal | server/auth/principal.js | роль, clientId и factoryId берутся из учётной записи, а не из запроса |
| Сервис | server/auth/authService.js | регистрация клиента, вход, выход, ограничитель попыток |
| HTTP | server/auth/authHttp.js, server/httpServer.js | `/api/v1/auth/*`; httpOnly-cookie превращается в Bearer для существующего адаптера заказов |
| Запуск | server/index.js, server/config.js | две отдельные DB-роли (заказы с RLS, вход) |
| Разработка | server/dev/ | PostgreSQL 17 в Docker, роли БД, вымышленные пользователи |

## Модель

- Три роли политики доступа: client, factory, partner. Публичная регистрация создаёт **только клиента**; фабрики и партнёры заводятся вне API (dev-seed или DBA). Поля `role`, `tenantId` в запросах отвергаются.
- Один tenant на процесс (`GABER_TENANT_ID`): партнёр GABER является оператором tenant.
- cookie `gaber_sid`: `HttpOnly`, `SameSite=Lax`, `Secure` в production; токен в теле ответа не возвращается. Изменяющие запросы с чужим `Origin` получают 403.
- Роль БД заказов не имеет доступа к `gaber_auth` (проверено тестом); роль входа не видит журнал заказов.
- **MFA не реализован.** Политика требует MFA для записей партнёра и фабрики, поэтому без него они отклоняются (`MFA_REQUIRED`). Для разработки есть флаг `GABER_DEV_ASSUME_MFA=1`, он запрещён при `NODE_ENV=production`.

## Запуск для разработки

```sh
cp server/dev/dev.env.example server/dev/dev.env   # не коммитится
npm run dev:db      # PostgreSQL 17, контейнер gaber-v04-pg, порт 55482
npm run dev:setup   # миграции 001-008, DB-роли, вымышленные пользователи
npm run server      # http://127.0.0.1:8788
npm run test:auth-e2e
```

Пользователи и пароли разработки лежат только в server/dev/seed-data.js.

## Проверка

- tests/auth-service.test.js: логика сервиса без базы (8 тестов).
- server/tests/auth-http-e2e.mjs: реальный HTTP, журнал заказов и PostgreSQL 17 с RLS: регистрация, вход, cookie, чужой заказ 404, истечение, выход, блокировка, ограничитель, MFA, разделение DB-ролей (41 проверка). В CI запускается в job postgres-staging.

## Интерфейс на сервере (маршрут #orders)

Раздел «Заказы · сервер» подключён к HTTP: вход и регистрация клиента, список заказов роли (`GET /api/v1/orders`, роль-DTO, чужие заказы в список не попадают), создание заказа из текущей конфигурации, действия клиента, партнёра и фабрики по этапам (назначение фабрики, ТЗ и расчёт, подтверждение, предложение, принятие, оплата, производство, отгрузка, спор) и сообщения по каналам. Решение всегда принимает сервер, интерфейс показывает понятные причины отказа (MFA, этап, устаревшая версия). Данные только демонстрационные.

Проверка: tests/server-orders-ui.mjs (интерфейс по настоящему редьюсеру и роль-DTO, сервер в памяти) и ручной прогон в браузере на PostgreSQL 17: клиент → партнёр (назначение, ТЗ) → фабрика (подтверждение, цена клиента скрыта) → партнёр (предложение) → клиент принимает.

### Оплата и PRODUCTION HOLD

- **Оплата проверена на реальной PostgreSQL** (server/tests/order-lifecycle-e2e.mjs, 51 проверка): клиент заявляет оплату (не считается учтённой), партнёр записывает аванс и остаток, аванс округляется вверх до копейки, повтор номера документа и переплата отклоняются, фабрика платежей и цены клиента не видит, банковского подтверждения нет нигде (`verifiedBankKopecks: null`).
- **Производство, контроль качества, отгрузка, доставка, приёмка и спор на сервере закрыты намеренно.** Журнал (`server/orderJournalService.js`, список `forbidden`) отвечает `EXTERNAL_AUTHORITY_REQUIRED` на start, complete, quality_pass, ship, deliver и accept_delivery: для них нужны внешние полномочия (банк, допуск производства, перевозчик), которых в системе нет (ворота G4–G7 в RELEASE-REVIEW-GATES). Поэтому реальный заказ останавливается после принятия предложения и оплаты. Интерфейс не показывает эти кнопки и объясняет причину.
- Без симулятора этих этапов на сервере нет. С симулятором (см. ниже) они проходят на реальной PostgreSQL; формы дополнительно проверены в tests/server-orders-ui.mjs по настоящему редьюсеру.

### DEV-симулятор внешних полномочий

Чтобы на демо заказ дошёл до производства, отгрузки, доставки и спора, есть **явный dev-симулятор** (`server/devExternalAuthority.js`, флаг `GABER_DEV_SIMULATE_EXTERNAL_AUTHORITY=1`).

- Он снимает HOLD только для шести команд (start, complete, quality_pass, ship, deliver, accept_delivery) и двух действий политики (`production.start`, `shipments.confirm_carrier`). Роли, MFA, этап и правила редьюсера остаются в силе: клиент и партнёр по-прежнему не могут запускать производство и подтверждать доставку.
- **Банк не имитируется:** `payments.verify_bank`, `payments.charge`, `payments.refund` и `factory.production_release` закрыты всегда, даже если передать их в grants (проверено тестом). `productionRelease.allowed` и `verifiedBankKopecks` остаются `false` и `null`.
- Защита от случайного включения: сервер не стартует с флагом при `NODE_ENV=production` или для tenant не из `TENANT-DEV*` и `TENANT-TEST*`. Без флага поведение не изменилось (HOLD).
- Сигналы: баннер «DEV-СИМУЛЯТОР» в интерфейсе (по ответу `/api/v1/auth/me`), заголовок `X-Gaber-Dev-Simulation`, запись в лог сервера на каждую симулированную команду.
- **Ограничение:** в самом журнале симулированные события не отличаются от настоящих, поэтому такой tenant нельзя считать источником реальных данных. Это демонстрация, а не банковская или производственная интеграция.
- Проверка: tests/dev-external-authority.test.js (5 тестов) и server/tests/order-simulated-lifecycle-e2e.mjs (55 проверок на PostgreSQL 17: оплата, производство, КК, отгрузка, доставка, приёмка и спор).

Прежние кабинеты `#projects`, `#factory`, `#partner` остаются локальной симуляцией на localStorage и не связаны с сервером.

## Что остаётся

- Старые кабинеты на localStorage не переведены на сервер, статусы и страницы партнёра (операции, смета) не подключены; в серверном разделе нет списка проектов конфигуратора, файлов и уведомлений.
- Реальный MFA, сброс пароля, подтверждение почты, ограничитель входа не в памяти процесса, `trust proxy`, ротация сессий, аудит входов.
- Онбординг фабрик и партнёров, реестр организаций, независимое ревью и пентест.
