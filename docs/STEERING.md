# GABER — как руководить проектом из GitHub

Это инструкция владельцу. Вся работа организована так, чтобы направление задавалось на GitHub, а исполнение шло по задачам.

## Как задавать направление

1. **Порядок.** Откройте Issues, отфильтруйте по этапу. Внутри этапа главный сигнал: метка `P0`, затем `P1`, `P2`. Меняйте метку или переносите задачу в другой этап.
2. **Решения владельца.** Задачи с меткой `решение владельца` ждут вашего ответа в комментарии: хостинг и режим стенда, юридическое, слияние в `main`, фабрика для пилота. Без вашего ответа они не двигаются.
3. **Новая идея.** Создайте issue: что нужно, зачем, как поймём, что готово. Чем чётче критерий готовности, тем точнее исполнение.
4. **Приёмка.** Работа приходит как Pull Request с описанием «проверено» и «не проверено». Прочитайте оба раздела; в PR указан SHA и результат `npm run gate`.
5. **Слияние в `main`.** Решаете вы, после независимого ревью (правило проекта). Шлюз на Mac ревью не заменяет.

## Правила, которые не меняются без вашего решения

- Данные, ставки и цены демонстрационные, пока нет реальной фабрики. В интерфейсе и материалах это названо.
- Реальные данные фабрики, бизнес-планы и пароли **не кладутся в репозиторий** (он раздаёт файлы публично через сайт лендинга и может быть открыт для ревьюера).
- Банк, перевозчик и допуск производства не имитируются в production; в демо есть явный dev-симулятор с баннером.
- Каждый PR проходит `npm run gate` на чистом SHA; пропуски шагов не считаются успехом.

## Как ставить задачу исполнителю

Дайте ссылку на issue и скажите, что делать: «возьми issue N и доведи до критерия готовности». Исполнитель обязан: сделать, прогнать шлюз, открыть PR с честным списком «не проверено», не сливать в `main` без вашего слова.
