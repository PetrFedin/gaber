# GABER — каноническая модель трёх сторон сделки

Обновлено 30.10.2026. Этот контракт **заменяет** прежний шестиролевой вариант.
**Единственный источник разработки:** [PR #2](https://github.com/PetrFedin/gaber/pull/2) в `feat/production-engineering-v04`. Релиз **PRODUCTION HOLD**.

## Роли

- **client — клиент:** самостоятельно создаёт 3D-конфигурацию, отправляет заявку, уточняет условия, видит утверждённую клиентскую цену, согласовывает ревизию, передаёт заявление об оплате, следит за этапами и принимает изделие.
- **factory — фабрика:** получает проектное ТЗ, внутренний состав конструкции (детали/мягкие слои/обивка/маршруты), своё вознаграждение за изготовление, подтверждает или возвращает ТЗ на корректировку, выполняет производственные операции при наличии отдельного допуска, QC/отгрузку и замечания.
- **partner — партнёр GABER, оператор платформы (мы):** видит все заказы **своего tenant**, готовит ТЗ, конструкторскую и производственную калькуляцию, плановую себестоимость фабрики, клиентскую цену, логистику и налоги, комиссию платформы, отправляет фабрике ТЗ, публикует клиенту предложение только после ответа фабрики, контролирует оплаты, сроки, спорные вопросы, финансовую и операционную аналитику.

Бренд/владелец/технолог/внешние партнёры больше **не отдельные аккаунтные роли**. Специалисты технологического процесса являются исполнителями внутри организации фабрики; их служебные действия следует оформлять отдельными полномочиями и журналом согласования, без добавления новых публичных ролей. Устаревшие роли из прежних тестов/документов недействительны.

## Данные каждой стороны

| Сведения | Клиент | Фабрика | Партнёр GABER |
| --- | --- | --- | --- |
| Собственный заказ/конфигурация | Да | Назначенное ТЗ | Все заказы собственного tenant |
| Клиентская цена, аванс и остаток | Да | Нет | Да |
| Предлагаемая цена изготовления фабрикой | Нет | Да | Да |
| Плановая комиссия и резерв GABER | Нет | Нет | Да |
| ТЗ, BOM, детали, технологии, проверки | Видимые параметры изделия | Полный концептуальный пакет | Полный концептуальный пакет |
| Подтверждение фабрики / возврат на переработку | Статус | Выполнить | Увидеть и управлять |
| Платёжное заявление клиента | Своё | По статусу готовности | Да |
| Проверенная банком оплата | Не реализована | Не реализована | Не реализована |
| Переход в реальное производство | Не разрешён | Не разрешён | Не разрешён |

**Безопасность:** доступ определяется проверенной серверной сессией и tenant + clientId / factoryId. Выбор вкладки в браузере не даёт серверных прав. Партнёр получает tenant-wide права только в своей организации, не в других tenant. Приватность денежных полей достигается **серверным DTO**, а не скрытием HTML. Демонстрационные проекты пока хранятся в localStorage и не должны содержать реальные данные клиентов.

## Сквозная последовательность и неизменные версии

```text
КЛИЕНТ: 3D-конфигурация → create / requested
ПАРТНЁР: расчёт экономики + ТЗ → prepare_spec / awaiting_factory
ФАБРИКА: confirm_spec → factory_confirmed
       или return_spec → factory_changes → партнёр готовит новую S2
ПАРТНЁР: offer(S1) → offered / R1, только после factory_confirmed
КЛИЕНТ: accept(R1) → accepted
КЛИЕНТ: report_payment → только клиентская заявка
ПАРТНЁР: record_payment → неподтверждённая локальная запись
ФАБРИКА: start / QC / ship → локальный сценарий; сервер запрещает реальную команду
КЛИЕНТ: accept_delivery / report_issue
```

Любое новое ТЗ создает S2 и требует **нового** фабричного подтверждения. Любая новая клиентская ревизия R2 сбрасывает прежнее согласие. Повторная отправка команды с тем же requestId идемпотентна; другая версия или полезная нагрузка с тем же ID — конфликт. Исправление финансовых условий без новой фабричной ревизии запрещено.

## Экономическая модель и точность

Все суммы — **целые копейки**. `src/partnerEconomics.js` вычисляет только план:
- `customerPriceKopecks`: публичная цена клиента после подтверждения фабрикой;
- `factoryCostKopecks`: плановая цена изготовления, показывается фабрике;
- `platformCommissionKopecks`: плановая комиссия GABER, видна только оператору;
- `logisticsKopecks`, `taxKopecks`, `otherCostsKopecks`: отдельные плановые статьи;
- `plannedReserveKopecks = customerPrice - factoryCost - commission - logistics - tax - otherCosts`.

Расходы не могут превышать клиентскую цену, значения не могут быть NaN, дробными копейками, отрицательными или неограниченно большими. **Плановая комиссия не является заработанной**, а запись оплаты не является банковским settlement. Никаких утверждений о фактической валовой прибыли, GMROI или выручке до подтверждённых документов.

`src/costing.js` содержит **демонстрационные** нормы. Стоимость фабрики в коммерческом ТЗ пока вводится оператором, не автоматически подтверждается производством и не является фактической закупочной ценой. Нужны заводские цены материалов, SKU, раскрой, операции, накладные, доставка и верификация контрагента.

## Где реализовано

- `server/accessPolicy.js` — только `client/factory/partner`, membership/MFA, tenant-wide партнёр.
- `server/orderCommandAdmission.js` — разрешённые команды из проверенной сессии.
- `src/orderWorkflow.js` — состояния, документ S1/S2, фабричное подтверждение, R1/R2, локальные оплаты.
- `src/partnerEconomics.js` — расчёт в копейках.
- `server/orderReadModel.js` — три изолированные серверные проекции, проектная BOM/техническая упаковка фабрики.
- `src/OrderWorkspace.jsx`, `src/OperationsPage.jsx`, `src/App.jsx` — три видимых демонстрационных кабинета, контроль цены и комиссии партнёром.
- `server/migrations/004_three_role_platform_hold.sql` — **неприменённая** staging-миграция; ограничивает новые команды в PostgreSQL. Старые immutable события требуют DBA-аудита при миграции.

## Тесты и стоп-критерии

Ключевые сценарии:
1. Клиент создал заказ, фабрика не может назначить клиентскую цену, партнёр подготовил ТЗ.
2. Фабрика возвращает ТЗ: партнёр не может опубликовать клиенту цену, пока не будет нового подтверждения.
3. Цена, фабричная стоимость и комиссия целиком разделены в ответах трёх API-сессий.
4. Истёкшая сессия, чужой tenant, чужой clientId/factoryId, MFA off, stale version и повторный запрос не позволяют обойти ACL.
5. Клиентский claim и локальная платёжная запись партнёра не открывают реальный `production.start`.

**Не завершено:** GitHub Actions GREEN, реальный Node+Chromium E2E, PostgreSQL 17/RLS/004 migration, авторизация с отзывом токенов, UI→HTTP→DB вместо localStorage, платёжный шлюз, подписание и утверждение CAD/BOM, поставщики/QC/отгрузка. Пока это кодовый интеграционный кандидат — **не готовый производственный продукт**.

После восстановления runner: `npm ci && npm run verify:source && npm test && npm run build` на **одном SHA**; review → merge `main` → чистый повторный checkout/build; затем PostgreSQL и независимые браузерные сценарии.

## Инвариант отзыва коммерческого предложения после изменений (31.10.2026)

Найден и устранён разрыв между локальным журналом и клиентским отображением: после `request_change(R1)` старое подтверждение `S1`/цена `R1` ранее оставались видимы как будто действуют, хотя `acceptedRevisionId` уже сбрасывался. Это могло вводить в заблуждение при оформлении платежа.

**Теперь на каждом чтении клиентского заказа:**

1. Действующее `offer` разрешено показывать только при стадии `offered/accepted/production/quality/ready/shipped/delivered/disputed/closed`, если **последнее** `spec.id` совпадает с `revision.specId`, `spec.status=published_to_client` и фабричное `factoryDecision` содержит корректное концептуальное подтверждение.
2. При `change_requested`, `awaiting_factory`, `factory_changes`, `factory_confirmed`: `offer=null`, `revisionId=null`, `dueDate=null`, поля платежа к действующему предложению = `null`. Предыдущий `R1` остаётся лишь в **истории**; новая конфигурация фабрики не попадает в клиентский DTO до публикации `R2`.
3. После `confirm_spec(S2)` клиент всё ещё не получает цену: требуется **отдельная** команда `partner.offer(S2)`. После публикации `R2` согласие по `R1` не наследуется.
4. Агрегат оператора `offeredKopecks` учитывает только опубликованные действующие предложения. Денежные **локальные** записи на отозванной ревизии не исчезают: до публикации новой они учитываются отдельно как `pendingRequoteLocalKopecks`, после появления `R2` — как `unallocatedPriorCreditKopecks`; это не банковские остатки.
5. Локальный клиентский кабинет показывает предупреждение об отзыве `R1` без старой цены/акта фабрики. Полная выгрузка сырого локального журнала (включая себестоимость и комиссию) доступна в **демонстрационном интерфейсе только партнёра**. Это не серверный контроль доступа: localStorage остаётся читаемым пользователем браузера.
6. Исторические служебные записи `prepare_spec/confirm_spec/return_spec/record_payment` не отображаются как полная операторская история на клиентском экране. В API все ответы формирует серверный DTO после проверки членства и целостности.
