# GABER — карта проекта и правила развития (v0.4.16)

## Статус
Главный источник кода: GitHub `PetrFedin/gaber`. Рабочая инженерная ветка `feat/production-engineering-v04`, Draft PR #2. `main` — отдельная стабильная ветка, не тождественная инженерной версии. Производственный выпуск: **HOLD**.

Этот документ описывает **наличие кода**, а не факт заводского внедрения или прохождения CI.

## Сквозной сценарий
`Конфигурация → геометрия и BOM → предварительная себестоимость → проект → локальная заявка → предложение Rn → согласование → локальные платежные записи → условная работа → QC → отгрузка → доставка → претензия → принятие`.

На каждом переходе должны сохраняться точная ревизия, действующая версия заказа, автор действия, категория доказательства, источник финансовой записи. Для нового серверного слоя все авторы и объекты определяются **только из доверенной серверной сессии и БД**.

## Ролевые границы
- Клиент: только собственные проекты, утверждение и изменение собственного предложения, претензии, приемка.
- Фабрика: назначенные изделия, нормирование, технический контроль, производственные операции.
- Бренд: собственный каталог и назначенные коммерческие задачи.
- Партнер: только назначенные объекты, ограниченная аналитика.
- Владелец: управление участниками и аналитика исключительно своего tenant.
- Технолог: проверка документации, но **не** автоматический допуск выпуска.

Локальная UI-перспектива не дает полномочий; `server/accessPolicy.js` пока контракт, не подключенная система авторизации.

## Правила интеграции
- Новый функционал вводится с трассировкой `UI → домен → данные → права → тест → документация`.
- Каждый PR обязан ссылаться на issue, указывать затронутые роли, изменения контрактов, критерии приемки, обратную совместимость.
- Хранение денег — в целых копейках; ввод валюты, налоги, отходы и доходность документируются раздельно.
- Коммит в GitHub не является выпуском. Требуется GREEN `npm ci && npm test && npm run build` на одном SHA, ролевые браузерные сценарии, затем отдельная заводская валидация.
- Нельзя подменять подтвержденную выручку локальными платежными строками, а утвержденный BOM — схематическим 3D.
